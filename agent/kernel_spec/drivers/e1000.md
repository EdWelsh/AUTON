# e1000

Written second, deliberately, and **without adding a field** — the bar `firecracker.md` set for
the target format. It differs from `virtio-net.md` on every axis the format claims to express:
one device id instead of three, one transport instead of two, `port` instead of `synthesize`,
`implemented` instead of `specified`, and a `source` where the other has a `specification`.

## What it drives

The Intel 82540EM, and only that. `8086:10d3` (82574L, the `e1000e` part) is a different
controller with a different descriptor format and belongs in its own record — listing it here
would claim this driver binds to hardware it has never been run against.

It is also the reason the QEMU PC is the only machine AUTON can currently build a network image
for. That is a statement about the tree, not about this driver.

## Why `port` rather than `synthesize`

The register set came from Intel's public Software Developer's Manual, which is a datasheet
rather than an open specification: it can be read and implemented from, and the register offsets
and bit meanings it documents are facts. No code was copied, and `source` says so — the field
exists because a ported driver with an unrecorded origin becomes a legal question at distribution
time, which is long after anyone can answer it cheaply.

## Verification

`scripts/run-acceptance.sh` already asserts both markers; this record names the check that
existed rather than inventing one. That is what `status: implemented` is allowed to mean.
