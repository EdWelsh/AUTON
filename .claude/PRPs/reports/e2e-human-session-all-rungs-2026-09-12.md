## What was run, and what it is not

Three 55-turn sessions — rule engine, rung-3b fp32, rung-3c int8 — driven by
`scripts/session.sh`. **These are automated, not human.** The plan asked for a person at the
keyboard for twenty minutes; that was not available, so the session's machine-checkable
properties were automated instead and the rest is named as a gap.

| Property | Automated? | Notes |
|---|---|---|
| Duration / multi-turn | yes | 55 turns, one continuous serial session |
| Consistency | yes | same question at turn 0 and turn 52 |
| Statefulness | yes | hostname set at turn 1, read at 26 and 53 |
| Stability over length | yes | answered-rate, first half vs second |
| Novel input | **partly** | generated by the host Ollama model, filtered against corpus and eval set |
| A person's surprise | **no** | not reproducible by automation — see Limits |

The plan's own risk table flags *single-operator bias: the developer asks only what they know
works*. With this repo's author driving, that is worse, not better — the same author wrote the
eval set **and** the training corpus. The mitigation is structural rather than aspirational:
turns come from a model that has never seen either, and anything colliding with either is
dropped mechanically.

## Findings

Every finding gets exactly one disposition.

### F1 — int8 and fp32 diverge. The Phase 3c claim was too strong. **DEFECT**

Asked *"what's the kernel version?"*:

```
fp32: …I do not know about that.
int8: …I do not know about the weather.
```

Phase 3c reported byte-identical answers across all 50 eval prompts and I concluded
**"quantization cost zero behavioural change."** That conclusion was wrong — it was a property
of the eval set's coverage, not of quantization. A 53-turn session outside that set found
divergence on the second try, and the int8 answer is the worse one: "the weather" is a
hallucinated topic for a kernel-version question.

This is exactly the failure Phase 7 exists to catch — the Phase 6 score becoming a target,
and a claim being made about the score rather than about the system.

*Disposition*: promoted to `tests/eval/prompts.jsonl` as `ses-06`, and it now appears in the
fp32-vs-int8 eval diff. The 3c report has been corrected.

### F2 — Shell commands are deflected for facts AUTON knows. **EVAL PROMPTS**

The generated operator typed shell idioms at the chat prompt — something I never considered
when writing the eval, which is entirely in natural language:

| Typed | Response | But AUTON knows |
|---|---|---|
| `ip a` | rule: generic deflection / **neural: correct IP** | 10.0.2.15 |
| `uname -a` | deflected | arch, kernel identity |
| `lsmod` | deflected | e1000 is loaded |
| `netstat -tulnp` | deflected | web :80, dns :53 |
| `meminfo` | deflected | 255 MB |
| `ls /sys/class/net` | deflected | the NIC |

7 of 49 generated turns were shell-style. A person sitting at a text prompt types shell
commands; the eval set assumed they would not.

*Disposition*: six promoted as `ses-01`…`ses-08`. Not a defect — deflecting is honest — but
the eval should measure it, and it now does.

### F3 — `ip a` is real generalisation by the neural model. **NO ACTION (good news)**

The rule engine deflects `ip a`; the 3b neural model answers `My IP is 10.0.2.15 (gateway
10.0.2.2, dns 10.0.2.3).` That string is in neither the corpus nor the eval set — the model
mapped an unseen shell idiom onto the right fact.

It is the clearest evidence yet that rung 3b learned something beyond phrasing recall, and it
argues against the rung-3b report's flat characterisation of the model as nearest-neighbour
retrieval. Recorded because good behaviour deserves evidence too.

*Disposition*: promoted as `ses-01` with an expected substring, so it becomes a regression
guard rather than an anecdote.

### F4 — The neural model declines a question the rule engine answers. **EVAL PROMPT**

*"which roles are available?"* — the rule engine lists the roles; the 3b model declines. A
straight regression on a capability AUTON has.

*Disposition*: promoted as `ses-05` so the next rung is scored on it.

### F5 — Sessions cannot distinguish "declined" from "should have declined". **NO ACTION**

34 of 49 novel turns were declined by the neural rungs. The harness counts declines but cannot
judge whether each was right — that is the Phase 6 rubric's job, and it needs a graded
expectation per prompt.

*Disposition*: no action. The promotion path (F2) is the mechanism: a decline worth judging
becomes an eval prompt with a bucket.

## Limits

**No human ran these.** A person would have noticed things this cannot: that an answer is
technically right but oddly worded, that the same fact is phrased three different ways across
a session, that a reply is condescending or too terse. The harness checks four properties it
was told to check. A person checks everything, including properties nobody enumerated.

**The generated turns are still a model's idea of a user.** gemma4 has not seen our corpus,
which removes the worst bias, but it produces plausible-operator text, not real intent. The
shell-command cluster (F2) is genuinely useful *because* it was unanticipated — but a person
would have produced stranger and more varied input.

**Rung 3a could not be sessioned.** Its model was overwritten during Phase 3b (`SLM/work/` is
gitignored and regenerated per run). The 3a baseline survives only as recorded scores in
`e2e-rung3a-baseline.md`.

**Recommendation**: run one real human session before trusting rung 3b in front of anyone.
This harness is a regression net, not a substitute — it should run every rung, and a person
should still sit down once.
