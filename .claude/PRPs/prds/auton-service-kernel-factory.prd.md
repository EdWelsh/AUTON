## Problem Statement

AUTON's kernel already answers "be a web server" and "be a DNS server" for real, and its
role registry advertises five more services — file, email, database, SSH, DHCP — as honest
`CAP_ROADMAP` rows that have sat unimplemented. Meanwhile the repo contains a complete but
unused kernel-generation apparatus: eleven subsystem specs, a HAL contract, an architecture
registry, ten role agents, and three validators including one built specifically to catch
composition failures. Nothing connects them. Until this week every service had to be hand-written into a single monolithic image that
compiled every source file in the tree, so adding a service made every other deployment
bigger and no service could ship on its own. That tree is now retired (see the correction
above), which removes the carving problem but leaves the generation problem untouched: there
is still no path from a service spec to a bootable image.

## Evidence

- `kernel/slm/roles.c` declares 7 distinct services. **2 are `CAP_WORKING`** (web via
  `http_server_run`, DNS via `dns_server_run`). **5 are `CAP_ROADMAP`** with honest blockers
  recorded in the source: file *"needs a filesystem"*, email *"needs SMTP/IMAP and mail
  storage"*, database *"needs persistent storage and a query engine"*, SSH *"needs crypto
  (key exchange, ciphers) and a PTY"*, DHCP *"this host is a DHCP client; serving leases is next."*
- `kernels/x86_64/Makefile` line: `CSRC := $(shell find kernel -name '*.c')`. **The build
  has no notion of subsystem selection.** Every image contains every service, unconditionally.
- The generation apparatus exists and is idle: `agent/kernel_spec/subsystems/` (boot, dev,
  drivers, fs, ipc, mm, net, pkg, sched, slm, sys), `agent/kernel_spec/arch/` (x86_64,
  aarch64, riscv64, hal), `agent/orchestrator/agents/` (architect, developer, reviewer,
  tester, integrator, manager, model_architect, training, data_scientist, base),
  `agent/orchestrator/validation/` (build, test, **composition**).
- `CompositionValidator` was written for exactly this problem — its docstring: *"Detects the
  Frankenstein composition effect… Locally correct subsystems interact to yield globally
  suboptimal or incorrect behavior."* It has never been run against a composed service image.
- **There is no dynamic memory allocation.** No `kernel/mm/`; `kernel_main.c` prints
  `[MM] PMM initialized` above the comment *"Minimal physical memory accounting (bitmap PMM
  lands later)."* Every buffer in the kernel today is static.
- **There is no filesystem and no storage driver.** No `kernel/fs/`, no AHCI/NVMe/ATA code
  anywhere. Two of the five roadmap services are blocked on this single gap.
- **There is no scheduler or process model.** No `kernel/sched/`; the marker is a stub by its
  own comment. `serve.c` is a single `hlt`/`net_poll` loop — the kernel does one thing at a time.

## Proposed Solution

Turn AUTON into a **unikernel factory**: one service spec in, one minimal bootable image out.
This is a smaller leap than it sounds, because *AUTON is already accidentally a unikernel* —
single address space, identity-mapped, no processes, no scheduler, one purpose, one serve
loop. The architecture the roadmap would otherwise have to invent is the architecture it
already has. What's missing is selection and generation: make the build manifest-driven
instead of glob-driven — now a question of what to *generate* rather than what to select,
since the monolith is gone — define a service-spec format alongside the existing subsystem specs,
and point the idle agent loop at it — architect drafts against the spec, developer writes the
subsystem, the three validators gate it, and the output is `auton-dns.iso` rather than a patch
to a monolith.

Sequence it to prove the machinery on the cheapest possible service before spending on the
expensive ones, and build the two shared unlocks (allocator, storage+filesystem) only when a
service actually needs them.

## Key Hypothesis

We believe a manifest-driven build plus a service-spec layer will let the existing agent loop
produce a working, minimal, bootable kernel per service.
We'll know we're right when `auton-dhcp.iso` is generated from a spec, is substantially
smaller than the general image, boots, serves real DHCP leases to a real client, and a second
service goes through the same pipeline in materially less time than the first.

## What We're NOT Building

- **A multi-service kernel.** One image, one service, by design. Running three services means
  three VMs. Multi-tenancy would require the scheduler and process model that don't exist and
  aren't in scope.
- **A general-purpose filesystem.** The storage lane delivers the minimum a file server and a
  key-value store need — read/write, flat or shallow hierarchy. Not POSIX, not journaling.
- **A package manager runtime.** `pkg.md` specifies one; it stays a spec. Services are baked
  into images at build time, not installed at runtime.
- **Fully autonomous generation.** The agent loop drafts and validates; a human reviews and
  approves every service before it ships. The factory is a force multiplier, not an oracle.
- **Production-grade protocol implementations.** These are minimal, correct-for-the-happy-path
  servers matching the existing HTTP/DNS bar — not hardened daemons. Stated in each image's docs.
- **Cryptographic self-invention.** The SSH lane ports a vetted implementation or is cut. No
  hand-rolled ciphers.

## Open Questions

- [ ] Where does the service-spec format live — extend `kernel_spec/subsystems/` (consistent,
      but conflates "kernel subsystem" with "deployable service") or a new
      `kernel_spec/services/` tree? Leaning the latter, since a service is a *composition* of
      subsystems plus an entry point, not a subsystem itself.
- [ ] How are subsystems declared and selected? A per-service TOML manifest listing subsystems
      and feature flags, or Kconfig-style symbols? TBD — the manifest is simpler and matches
      the repo's existing TOML habit.
- [ ] Does the SLM belong in a service image at all? A DHCP appliance arguably needs no chat —
      but "every AUTON image is talkable-to" is the project's identity. Suggest: chat is a
      manifest flag, default on, and a headless variant proves the selection machinery works.
- [ ] Is the same neural model right for a single-purpose appliance, or does each service want
      a service-specific fine-tune? Interesting and unresolved; interacts with PRD #1's rung 3b.
- [ ] Which filesystem? A minimal custom FS is faster to write but unreadable from a host;
      FAT32 is verbose but lets you inspect the image from macOS/Linux. **Leaning FAT32** for
      exactly that debuggability.
- [ ] SSH realistically needs a vetted crypto implementation in freestanding C. Is there a
      portable candidate that compiles with no libc? If not, SSH should be cut rather than
      hand-rolled.
- [ ] Does each service image need its own network config story (static IP vs DHCP client)?
      A DHCP *server* that is itself a DHCP *client* is a bootstrap problem.

## Users & Context

**Primary User**
- **Who**: The AUTON developer, wanting AUTON to produce useful artifacts rather than only
  demonstrate itself.
- **Current behavior**: Hand-writes each service directly into the single kernel; every
  service ships in every image; the whole generation apparatus sits unused.
- **Trigger**: Wanting a real appliance — "I need a DNS server on the LAN" — and wanting the
  agent loop to earn its existence by producing one.
- **Success state**: Describe a service, get a bootable minimal image, boot it, use it.

**Job to Be Done**
When I need a small dedicated network service, I want to describe it and have AUTON generate a
minimal bootable kernel that does only that, so I get a real appliance instead of another
roadmap row.

**Non-Users**
Not for people wanting a general-purpose server OS — that's Linux. Not for multi-service
consolidation. Not for production workloads where the protocol implementation's maturity matters.

### MVP Scope

Phases 1–4: a manifest-driven build, a service-spec format, the shared allocator, and
`auton-dhcp.iso` — generated from a spec, minimal, booting, and handing a real address to a
real client. That alone proves the factory; every later service is a repeat with a bigger
payload.

### The Architectural Insight

AUTON is already a unikernel and nobody wrote it down. It has:

| Unikernel property | AUTON today |
|---|---|
| Single address space | Identity-mapped, no user/kernel split |
| No process model | Confirmed absent — no `kernel/sched/` |
| One purpose per image | `serve.c` = one `hlt`/`net_poll` loop |
| Library-OS composition | 11 subsystem specs already carved this way |
| Boots directly on a hypervisor | Multiboot2 + GRUB, already working |

The per-service-image choice therefore adds **no** architectural debt — it names what the code
already is. The gap is purely build-time selection and spec-driven generation.

## Technical Approach

**Feasibility**: **HIGH** for the build/manifest/spec machinery and the DHCP service.
**MEDIUM** for storage + filesystem and the services on top. **LOW** for SSH (crypto) and
for genuinely autonomous agent-loop authorship.

**Architecture Notes**
- **The one-line change that unlocks everything**: `CSRC := $(shell find kernel -name '*.c')`
  becomes a manifest-resolved source list. Everything else in this PRD is downstream of it.
- **Selection must be real, not cosmetic.** Verify with `nm`/size that unselected subsystems
  are genuinely absent from the binary — a build that still compiles everything and merely
  skips registration would pass a naive test and defeat the purpose.
- **Reuse, don't rebuild.** `BuildValidator`, `TestValidator`, and `CompositionValidator`
  already exist. The factory is a new *consumer* of the orchestrator, not a new orchestrator.
- **The PMM gates everything after DHCP.** A lease table can be a static array; a filesystem
  cache and a query engine cannot. This is the same bitmap allocator the Win/Linux PRD needs
  for real hardware — build it once, in whichever PRD reaches it first.
- **Storage is the pivotal unlock**: one block driver (start with QEMU's virtio-blk or ATA
  PIO — simple, well-documented, no DMA ring subtleties) plus one minimal filesystem turns
  *two* roadmap rows green. It is the highest-leverage unblocking work in the document.
- **Service networking bootstrap**: a DHCP *server* cannot obtain its own address by DHCP.
  Service images need a static-IP path in the manifest, which the current `net_bringup`
  (DHCP-only) does not have.
- **Every hard-won networking lesson carries forward** to every service image: `volatile`
  descriptor rings, `hlt`-yielding poll loops or TCG starves RX, pre-resolved gateway ARP.
  Encode these in the spec as required patterns so the agent loop reproduces them rather than
  rediscovering them.
- **Chat stays in by default.** Every AUTON image should be talkable-to; a headless flag
  exists mainly to prove the selection machinery genuinely removes code.

**Technical Risks**

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| Subsystem selection turns out to be deeply entangled (everything includes `kernel.h`, calls `kprintf`, registers into `roles.c`) | **H** | Phase 1 starts with a dependency audit, not a Makefile edit. Expect to define a small mandatory core and make only leaves optional at first |
| The agent loop can't produce a working subsystem | **M** | A human walks the path for service #1; the loop attempts service #2 with that as a worked example. Loop authorship is a `Could`, never a blocker |
| Local model quality insufficient for kernel C | **M** | Depends on PRD #1 Phase 1. Fall back to human-authored + agent-reviewed, which still exercises the validators |
| Filesystem choice is regretted later | **M** | FAT32 for host-inspectability; the format is behind a small VFS-ish interface so a swap is contained |
| SSH crypto has no viable freestanding port | **M** | Pre-committed: cut SSH rather than hand-roll. Written into the scope above |
| Service images drift from the general kernel (bug fixed in one, not the other) | **M** | Shared subsystems stay one source of truth; only composition differs. The composition validator runs across all images |
| Image count outgrows the test harness | **L** | Marker sets are per-service data files, not new harnesses |

### Phase Details

**Phase 1: Dependency audit + manifest build**
- **Goal**: The build can produce an image containing only what a service needs.
- **Scope**: Audit real coupling first — who includes what, who calls `kprintf`, what registers
  into `roles.c`, what `kernel_main` unconditionally calls. Define a mandatory core versus
  optional leaves. Replace the `find`-based `CSRC` with a manifest-resolved list. Add a size/
  symbol assertion proving omitted subsystems are absent from the binary.
- **Success signal**: A general image and a deliberately-reduced image build from the same tree,
  and `nm` proves the reduced one is genuinely missing the omitted symbols.
- **Expect**: more entanglement than hoped, especially around `roles.c` registration and
  `kernel_main`'s fixed call order. Budget for a small refactor, not just a Makefile edit.

**Phase 2: Service-spec format**
- **Goal**: A service is describable before it is written.
- **Scope**: `kernel_spec/services/<name>.md` + a manifest: required subsystems, feature flags,
  entry point, network config mode (DHCP client vs static), acceptance markers, and
  **required patterns** (volatile rings, `hlt`-yield, gateway pre-ARP) so the agent loop
  inherits the hard-won lessons instead of rediscovering them. Follows the house style of the
  existing `subsystems/*.md`.
- **Success signal**: `dhcp.md` written and reviewed as sufficient to implement from, before
  any implementation exists.

**Phase 3: Real PMM**
- **Goal**: Dynamic allocation, so services beyond DHCP are possible at all.
- **Scope**: Bitmap physical allocator over the real Multiboot2 memory map; reserve kernel and
  module regions; `kmalloc`/`kfree`; the `[MM]` marker reports true numbers; an acceptance
  test that allocates, frees, and re-allocates.
- **Success signal**: The `[MM]` marker becomes a true statement, asserted by a test.
- **Shared with**: `auton-windows-linux.prd.md` Phase B2 — identical work. Whichever PRD gets
  there first builds it; the other consumes it. Do not build twice.

**Phase 4: Service #1 — DHCP server**
- **Goal**: One real, minimal, bootable service image.
- **Scope**: Human-authored against the Phase 2 spec — this phase is proving the *factory*,
  so the service is deliberately the smallest available: no filesystem, no crypto, and the
  DHCP client half already exists to learn the wire format from. Add the static-IP manifest
  path (a DHCP server can't DHCP for itself). Lease table can be a static array; PMM optional here.
- **Success signal**: `auton-dhcp.iso` boots, a real client obtains a real lease, and the image
  is ≥ 40% smaller than the general kernel.

**Phase 5: Factory pipeline + gates**
- **Goal**: Turn the walked path into a command.
- **Scope**: `auton build-service <name>` driving spec → manifest → build → **CompositionValidator**
  → TestValidator → ISO. Per-service marker sets as data files consumed by the extended
  `acceptance_tests.py`. Critical composition issues fail the build.
- **Success signal**: DHCP rebuilds end to end from one command; an injected cross-subsystem
  defect is caught by the composition gate rather than at boot.

**Phase 6: Service #2 — agent-loop authored**
- **Goal**: The generation apparatus finally does the thing it was built for.
- **Scope**: Point architect + developer + reviewer + tester at a service spec with the Phase 4
  service as a worked example. Human reviews every line before merge. Record wall-clock cost
  against service #1 — that ratio is the factory's actual value.
- **Success signal**: A service subsystem substantially authored by the loop, passing all gates,
  at measurably lower cost than #1. **If the loop can't do it, that is a finding worth having**
  — record it and continue human-authored.

**Phase 7: Storage unlock — block driver + minimal FS**
- **Goal**: The single unlock that turns two roadmap rows green.
- **Scope**: One block driver (virtio-blk or ATA PIO — pick the simpler, avoid DMA ring
  subtleties for now) and FAT32 behind a small VFS-ish interface for later swapping. FAT32 is
  chosen specifically so an image can be mounted and inspected from macOS or Linux when
  debugging.
- **Success signal**: The kernel reads and writes a file that the host can then mount and verify.

**Phase 8: Service #3 — file server**
- **Goal**: Close the `file` roadmap row.
- **Scope**: Serve a docroot from the filesystem over the existing HTTP server. Mostly
  composition — HTTP exists, FS now exists.
- **Success signal**: `curl` retrieves a file that was written to the image's disk, not compiled in.

**Phase 9: Service #4 — key-value database**
- **Goal**: Close the `database` roadmap row honestly.
- **Scope**: A persistent KV store on the filesystem with network query verbs. Explicitly not
  SQL — `roles.c` says "a query engine," and a KV store is the honest minimum. Update the
  role note to match what was actually built.
- **Success signal**: Values survive a reboot; the role's description matches reality.

**Phase 10: Service #5 — SSH (gated)**
- **Goal**: Either a real SSH appliance or a documented, deliberate cut.
- **Scope**: **Gate first** — spike whether a vetted crypto implementation (key exchange,
  ciphers, MAC) ports to freestanding C with no libc. If yes, proceed: SSH + a minimal PTY-ish
  channel. If no, cut it, record why in `roles.c`, and move on.
- **Success signal**: Either an interactive SSH session into the AUTON chat, or a written
  decision not to hand-roll crypto. Both outcomes are acceptable; hand-rolled crypto is not.

**Phase 11: Service #6 — email server**
- **Goal**: The heaviest roadmap row, attempted only once everything it needs exists.
- **Scope**: SMTP receive + mail storage on the filesystem. IMAP out of scope for the first cut;
  receive-and-store is the honest MVP.
- **Success signal**: A real mail client delivers a message that survives a reboot.

**Phase 12: Catalogue + roles.c truth-up**
- **Goal**: The chat OS tells the truth about its own family of images.
- **Scope**: `roles.c` distinguishes "this kernel does it," "a dedicated AUTON image does it —
  here's how to build it," and "still roadmap." Chat answers `what can you do` accordingly.
- **Success signal**: Every row in the registry is verifiable, and "be an email server" gives a
  useful answer rather than only an apology.

### Parallelism Notes

- **1 ∥ 2 ∥ 3** — build machinery, spec authorship, and the allocator are independent. The
  spec can be written while the build is being untangled.
- **6 ∥ 7** — agent-loop authorship needs no storage; the storage unlock needs no agent loop.
- **8 ∥ 9** — file server and KV store both sit on Phase 7 and touch different code above it.
- **Strictly serial**: 1+2 → 4 → 5 → everything else. The factory must be proven on one service
  before it is trusted with more, and 3 → 7 → {8,9} because storage needs allocation.
- **Cross-PRD**: Phase 3 (PMM) is the same work as `auton-windows-linux.prd.md` Phase B2 —
  coordinate, don't duplicate. Phase 6 depends on PRD #1 Phase 1 (a local model that exists).
  The whole factory depends on PRD #1 Phase 2 (the E2E spine) for its verification.

## Decisions Log

| Decision | Choice | Alternatives | Rationale |
|----------|--------|--------------|-----------|
| Factory output shape | Per-service unikernel images | One kernel + loadable modules; composable both; codegen only | User selected. Also the honest description of what AUTON already is — single address space, no processes, one serve loop |
| Service ordering | Prove the factory on the smallest service first | Start with the most useful service | User asked for all services *and* prove-the-factory. Machinery validated cheaply before expensive payloads |
| First service | DHCP server | File, SSH, email | No filesystem, no crypto, and the client half already exists as a wire-format reference |

## Research Summary

**Market Context**
The unikernel prior art is directly relevant: MirageOS, IncludeOS, OSv, and Unikraft all build
single-purpose, single-address-space images from a library-OS composed at build time, and all
converge on the same three conventions — declarative manifests for subsystem selection,
one service per image, and no process model. AUTON arrives at that architecture from the
opposite direction (it never had processes to remove), which makes the pattern a fit rather
than a retrofit. The known industry failure mode is equally relevant: unikernels are hard to
debug because there is no shell and no process to inspect — which is precisely the gap
AUTON's in-image chat REPL closes. That is a genuine differentiator worth stating out loud.

**Technical Context (verified in-repo, 2026-09-10)**
- `roles.c`: 2 `CAP_WORKING` (web→`http_server_run`, DNS→`dns_server_run`), 5 `CAP_ROADMAP`
